### 0.2 术语表

| 术语 | 说明 |
| --- | --- |
| Lemma | 词元，一个词的词典原形（`running` → `run`，`better` → `good`） |
| 词形还原（Lemmatization） | 把屈折变化形式映射回 Lemma 的过程 |
| Headword | 词典条目头词，即用户查的那个词 |
| Front-coding | 把有序词条按"公共前缀长度 + 后缀"压缩存储的技术，索引体积可降 40%～60% |
| mmap | 内存映射，把文件直接映射进进程地址空间，随机读不需要 read() 拷贝 |
| FTS5 | SQLite 的全文检索扩展，支持倒排索引与 BM25 排序 |
| SymSpell | 基于"删除距离"的拼写纠错算法，预处理后查错是 O(1) 级哈希查表 |
| NMT | Neural Machine Translation，神经网络机器翻译 |
| ONNX / ORT | 开放神经网络交换格式 / ONNX Runtime 推理引擎 |
| int8 量化 | 把 fp32 权重压成 8 位整数，模型体积约 ÷4，CPU 推理提速 1.5～3 倍 |
| SentencePiece | 子词分词器，NMT 模型的输入前端 |
| OOV | Out-of-Vocabulary，词表外词，即"查不到" |
| Token 覆盖率 | 语料中能被词库解释的 token 占比，衡量词典覆盖能力的核心指标 |
| LEXD | 本项目自定义的词典二进制包格式（Lexicon Data） |
| ABI | 应用二进制接口，本项目主发 `arm64-v8a` |

## 1. 项目概述

### 1.1 一句话定义

**一款装完就能用、断网也能查、查一个词 0.1 秒内出结果的 Android 离线词典，专门为"读英文技术文档"这件事做优化。**

不是又一个大而全的词典，而是把三件事做到极致：

1. **查得到**——专八 13,000 词全覆盖，词形变化、短语、缩写、源码标识符都能命中；
2. **查得快**——输入即搜，本地索引 mmap 直读，不转圈、不联网、不弹广告；
3. **看得懂**——词条给技术语境下的释义排序，整句给离线机翻，术语按技术含义优先。

### 1.2 为什么必须离线

很多人会问：手机上不是有 Google 翻译、有道、欧路吗？为什么还要再造一个？

因为**读技术文档**这个场景，对"在线词典"极不友好：

| 维度 | 在线词典 / 云端翻译 | 本产品（全离线） |
| --- | --- | --- |
| 网络依赖 | 地铁、飞机、内网隔离环境、境外服务器被墙时不可用 | 断网、飞行模式、无 SIM 卡均可用 |
| 响应延迟 | 一次查询 300ms～2s（含握手、排队），输入联想常常卡顿 | 本地索引直读，P95 ≤ 8ms，输入即出 |
| 隐私 | 查询词、划词内容、整段文档上传到第三方服务器 | 所有文本不出设备，可给出"零网络权限"的硬证明 |
| 成本 | 免费版有广告 / 限次，去广告要订阅 | 一次安装，永久免费，无账号、无内购 |
| 稳定性 | 服务下线、接口变更、App 被下架即失效 | 装到手机上就永远能用 |
| 干扰 | 首页信息流、每日打卡、推送 | 打开就是搜索框 |

**关键判断**：技术文档阅读是**高频、短查询、强打断**的行为。读一页英文文档，可能要查 15～30 次词，每次都等 1 秒网络往返，阅读心流就断了。离线不是"锦上添花"，而是这个场景的**必要条件**。

### 1.3 场景痛点拆解

读英文技术文档时，真正卡住人的往往不是"不认识这个单词"，而是下面五种情况：

| 痛点 | 具体表现 | 本产品的解法 |
| --- | --- | --- |
| 术语密集且偏门 | `idempotent`、`serialization`、`backpressure`、`throttling` 通用词典释义不对味 | L4 技术术语表 20,000 条，技术义项排第一，附中文工程惯用译法 |
| 词形与派生 | 查 `deprecated` 查不到，得自己想到 `deprecate` | 词形还原 + 派生词剥离，5 级检索自动回退（第 6 章） |
| 源码标识符 | `getUserById`、`is_idempotent`、`HTTPStatusCode` 查不到 | 标识符拆词算法，camelCase / snake_case / 全大写缩写自动切分（6.4） |
| 长句读不懂 | 定语从句套三层，单词都认识但句子看不懂 | 本地 NMT 整句翻译，术语约束解码保证专业词不被乱译（第 7 章） |
| 查完就忘 | 查了 20 次同一个词 | 一键入生词本 + 间隔重复复习（10.6） |

| --- | --- | --- | --- |

### 1.5 明确不做的事（Non-Goals）

划清边界，防止范围失控：

- ❌ **不做在线词典兜底**。一旦引入网络查询，"离线"就变成营销话术，且需要服务器成本与隐私政策升级。v1.0 应用**不申请 INTERNET 权限**，这是最强的产品承诺，也是最省事的合规方案。
- ❌ **不做例句语音库 / 真人发音包**。版权与体积都不可控，v1.0 只有 IPA + 系统 TTS。
- ❌ **不做全文文档翻译（整篇 PDF/EPUB）**。渲染与版式还原是无底洞，v2.0 再议。
- ❌ **不做背单词主线产品**（词库课程、打卡、词汇量测试）。生词本只做"阅读的副产品"，不做学习 App。
- ❌ **不做账号与云同步**。同步必然要联网，与定位冲突；导出 CSV 由用户自行迁移。
- ❌ **不做 iOS / 鸿蒙**。技术栈为原生 Android，跨端需重写（v3.0 议题）。

### 1.6 用户画像与典型流程

**画像 A：后端工程师读官方文档**

> 32 岁，英语六级，读 Kubernetes / Postgres 文档。认识 90% 的词，但每段都有 2～3 个卡词；不想为查词切换 App 打断思路。

**画像 B：考研 / 专八备考学生读英文原版教材**

> 22 岁，需要"这个词是不是专八词"的提示，边读边收生词本。

**典型流程 1：主动查词**

```
① 点开词锋（冷启动 ≤ 400ms，直接落在搜索框，键盘已弹起）
      ↓
② 输入 "idem" → 第 3 个字符起联想列表实时刷新（每次 ≤ 8ms）
      ↓
③ 看到 "idempotent  a. 幂等的" → 点开词条页
      ↓
④ 词条页：音标 + 词性分组义项（技术义项置顶）+ 2 条技术例句 + 派生词 + 词频标签「专八」
      ↓
⑤ 点喇叭听发音；点☆加入生词本；左右滑动切上/下一个词
```

**典型流程 2：划词翻译（最高频）**

```
① 在 Chrome / 微信 / 任意 App 里长按选中 "the request is idempotent"
      ↓
② 系统文本选择菜单出现「词锋」→ 点击
      ↓
③ 词锋以半屏 BottomSheet 浮出，展示：
     · 逐词释义（每个词可点开完整词条）
     · 整句译文（NMT，约 0.8s，出字流式刷新）
      ↓
④ 下滑关闭，回到原 App，上下文不丢
```

### 1.7 竞品对照与差异化

| 产品 | 离线能力 | 专八词库 | 技术术语 | 划词 | 体积 | 主要短板 |
| --- | --- | --- | --- | --- | --- | --- |
| 欧路词典 | 支持导入 MDX | 需自备词库 | 弱 | 支持 | 30MB+ | 词库要自己找，配置门槛高 |
| 深蓝词典 | 支持 MDX | 需自备 | 弱 | 弱 | 20MB+ | 界面老旧，MDX 解析慢 |
| 有道词典 | 部分离线 | 有 | 中 | 支持 | 200MB+ | 广告、信息流、强联网 |
| Google 翻译 | 需先下载语言包 | 无词条 | 弱 | 支持 | 50MB+ | 无词条释义，无词形还原 |
| **词锋 LexForge** | **完全离线（无网络权限）** | **内置 L1/L2** | **L4 两万条** | **支持** | **36MB 起（标准包）** | 无真人发音、无整篇翻译 |

**差异化落点**：别人做"万能词典"，我们做"读技术文档的那把手术刀"。三个护城河：**检索延迟（毫秒级）**、**技术义项排序**、**源码标识符可查**。

### 2.2 非功能需求

| 类别 | 指标 | 目标值 | 测量方法 |
| --- | --- | --- | --- |
| 启动 | 冷启动到首帧 | ≤ 400ms（P95） | Macrobenchmark `StartupTimingMetric` |
| 启动 | 冷启动到输入可交互 | ≤ 800ms（P95） | 同上 |

### 2.3 词汇覆盖度：定义、分级与验收

这是本项目最容易被含糊过去的地方，必须量化。

**（1）分级策略**

| 级别 | 内容 | 词条数 | 体积（压缩后） | 分发方式 |
| --- | --- | --- | --- | --- |
| L1 | 专八核心高频词（含全部 CET-4/6 与考研词） | 8,000 | ≈ 7MB | 内置 |
| L2 | 专八全量（L1 + 其余专八大纲词） | 13,000 | ≈ 11MB | 内置 |
| L3 | 扩展通用词库（ECDICT 精选，含 GRE/TOEFL 及常用派生） | 400,000 | ≈ 60MB | 本地文件导入（侧载） |
| L4 | 技术术语与惯用译法 | 20,000 | ≈ 4MB | 内置 |

> **说明**：专八（TEM-8）考试大纲要求认知词汇约 13,000 个，其中熟练运用约 8,000 个。本项目的 L2 即按此口径构建，L1 取其中词频最高的 8,000 条用于"高频优先"排序与复习队列筛选。

**（2）覆盖度指标**

设测试语料 $T$ 共 $N$ 个 token，其中能被词库直接解释（精确命中 lemma）的为 $N_{hit}$，经词形还原/派生剥离/标识符拆词后能解释的为 $N_{norm}$，则：

- 直接覆盖率 $C_{raw} = N_{hit} / N$
- 有效覆盖率 $C_{eff} = N_{norm} / N$ ← **验收以此为准**

**（3）验收阈值与测算语料**

| 语料集 | 规模 | 用途 | 目标 $C_{eff}$ |
| --- | --- | --- | --- |
| 通用英文新闻（公开语料抽样） | 2M token | 基线校验 | ≥ 98.5% |
| 技术文档集（MDN / Kubernetes / PostgreSQL / Python 官方文档抽样） | 3M token | 主验收集 | ≥ 98.0% |
| 源码注释集（GitHub Top 500 仓库注释抽样） | 1M token | 边界场景 | ≥ 96.0% |
| 论文摘要集（arXiv cs 分类抽样） | 1M token | 边界场景 | ≥ 96.5% |

> 达不到 98% 的部分，**80% 会集中在专有名词（库名、协议名、产品名）与复合新词**。对策：① L4 术语表补足工程高频词；② 专有名词识别后不强行翻译，直接原样保留并标注"专有名词"；③ 报告明细，按词频导出 Top 500 未覆盖词作为下一版补词清单。

**（4）测算方法（可执行）**

```bash
# 1) 语料清洗：去代码块、去 URL、统一小写、保留原始 token 以便回溯
python tools/coverage.py corpus/ --strip-code --out build/coverage_norm.txt

# 2) 逐 token 判定
#    命中顺序与线上检索内核完全一致，避免"离线测算好看、线上查不到"
python tools/coverage.py --dict build/lexd/L2.lexd \
                          --glossary build/lexd/L4.lexd \
                          --lemma --deriv --identifier \
                          --report build/coverage_report.csv

# 3) 输出
#    totals: tokens=3,102,441  raw=91.3%  eff=98.24%  oov_unique=11,904
#    build/coverage_report.csv 列: token, freq, hit_stage, suggestion
```

**三条硬规则**：

1. **词典只读**。`.lexd` 打包进 APK assets，永不写入，用 mmap 直读；用户数据（生词本、历史、设置）走 SQLite。
2. **查词不上线程池排队**。单次查询是纯 CPU 的短任务（微秒~毫秒级），在 `Dispatchers.Default` 上直接跑，不做任务队列，避免调度开销。
3. **翻译才用协程 + 可取消**。NMT 是百毫秒级任务，必须有 Job 取消、进度回调与内存上限。

### 3.4 线程与并发模型

| 场景 | 调度 | 说明 |
| --- | --- | --- |
| 输入联想 | `Dispatchers.Default`，`flatMapLatest` | 新输入自动取消上一次，天然防抖 |
| 词条详情加载 | 同上 | 词条已随联想结果返回摘要，详情页只补例句 |
| 翻译 | `Dispatchers.Default`（ORT 内部再开线程） | ORT `intra_op_num_threads = min(4, cores/2)` |
| 词库安装/校验 | `Dispatchers.IO` | 大文件 IO，带进度回调 |
| 数据库写 | `Dispatchers.IO` + 单写队列 | 生词本写入频繁但量小，串行即可 |

**加锁策略**：`LexiconStore` 内部所有结构不可变（构建期定型），因此**读路径完全无锁**；只有"扩展词库挂载/卸载"时需要 `StampedLock` 写锁保护引用替换，读侧用乐观读。

### 3.5 关键设计决策（ADR 摘要）

| ID | 决策 | 备选方案 | 结论与理由 |
| --- | --- | --- | --- |
| ADR-1 | 自研 LEXD 二进制包 + mmap，而非纯 SQLite | SQLite 单表查词 | SQLite 每次查询要过 B-Tree + 页缓存，实测 P95 约 3～8ms，且首查有 IO 抖动；自研前压缩索引 + zstd 块可做到 0.6ms，且体积小 30% |
| ADR-2 | 词条内容用 zstd 压缩块，非平铺 JSON | 明文 JSON | 明文 13k 词条约 45MB，压缩后 11MB；mmap + 按块解压兼顾体积与速度 |
| ADR-3 | Kotlin + Compose，非 Flutter | Flutter | 需要 mmap/直接文件描述符/NDK 级集成，Flutter 走 platform channel 反而更绕；Compose 冷启动经 Baseline Profile 可压到 400ms 内 |
| ADR-4 | ONNX Runtime Mobile + opus-mt，非 ML Kit 翻译 | ML Kit On-Device Translation | ML Kit 首次使用需从 Play 下载 ~30MB 模型，且依赖 GMS，违背"装完即离线"；ORT 方案模型随包，完全自持 |
| ADR-5 | 无 INTERNET 权限 | 保留权限做"可选增强" | 少一个权限 = 少一类合规问题 + 一个可对外宣传的硬承诺；扩展词库走本地文件导入而非在线下载 |
| ADR-6 | 词典包与代码分离版本号 | 单一版本 | 词库可独立迭代（补词、修错），不必为改 3 个词条发版；`packVersion` 与 `appVersion` 解耦 |

### 4.2 词条字段模型

```jsonc
{
  "id": 10237,                      // 全局唯一，构建期分配，稳定不变
  "hw": "idempotent",               // headword，小写，检索键
  "disp": "idempotent",             // 展示用大小写（如 "HTTP"、"iPhone"）
  "ipa": { "uk": "ˌaɪdəmˈpəʊtənt", "us": "ˌaɪdəmˈpoʊtnt" },
  "pos": [                          // 词性分组，顺序即展示顺序
    {
      "p": "adj.",
      "senses": [
        { "d": "（计算）幂等的：多次执行与一次执行结果相同的",
          "tag": "tech", "pri": 1 },
        { "d": "（数学）幂等的", "tag": "math", "pri": 2 },
        { "d": "（罕）同一的；相同的", "tag": "rare", "pri": 9 }
      ]
    }
  ],
  "ex": [                           // 例句，tech 语域优先
    { "en": "PUT is idempotent, so retrying the request is safe.",
      "zh": "PUT 是幂等的，因此重试该请求是安全的。",
      "src": "self" }
  ],
  "forms": ["idempotently"],        // 该词的派生/变形，供反向查找
  "deriv": { "base": null, "suffix": null },
  "freq": 18234,                    // 词频排名（越小越常用）
  "level": ["L2", "tem8", "gre"],   // 分级标签
  "gloss": ["幂等"]                  // 中文关键词，供中→英检索（构建期生成）
}
```

**字段裁剪原则**：为控制体积，`ex` 每词最多 3 条，`senses` 每词最多 8 条，`gloss` 最多 4 个；超出部分在构建期截断并记录到报告，避免"某个词 4KB 拖慢整包"。

```
⑦ 词频与分级：wordfreq 取 zipf 值 → 排名 → 打 L1/L2/L3 与 tem4/tem8 标签
   ▼
⑧ 敏感内容过滤：粗俗/歧视性词条保留但标注 `flag: restricted`，首屏不展示例句
   ▼
build/normalized/*.jsonl  → 供 LEXD 打包器使用
```

**校验规则（构建期硬失败）**：

| 校验项 | 规则 | 失败处理 |
| --- | --- | --- |
| 头词唯一 | `hw` 全局唯一 | 后者合并进前者义项 |
| 头词字符集 | 仅 `[a-z0-9 '\-.&/()]` 与合法扩展字母 | 丢弃并记入 `reject.log` |
| 空义项 | 每个词至少 1 个非空义项 | 丢弃该词 |
| 音标格式 | 匹配 `^[a-zɑɒæəɜɪʊʌθðʃʒŋˈˌː()\s-]*$` | 置空 |
| 例句长度 | 4～40 token | 超长截断或丢弃 |
| 词频缺失 | `freq` 为空时置 999999（排最后） | 不失败 |

预计丢弃率 3%～6%，属正常（多为缩写变体、复合词残片）。

### 4.4 专八分级表的构建

专八（TEM-8）没有官方开放的机读词表，必须自建，做法是**三源交叉 + 人工抽检**：

1. **来源 A：公开大纲词表**。收集可获取的 TEM-4/TEM-8 词汇表（按词形去重），得到约 13,000 条候选。
2. **来源 B：ECDICT 标签**。ECDICT 的 `tag` 字段覆盖 `zk/gk/cet4/cet6/ky/toefl/ielts/gre` 等考试标签，但 **TEM-4/TEM-8 标签在其主库中并不完整**，因此**不能**直接用标签当专八表，只能用于校验：一个词若同时带 `cet4` 标签却不在专八表中，需要复核（专八表本就包含四级词）。
3. **来源 C：词频约束**。用 wordfreq 的 zipf 值排序，检查分布合理性：专八 13,000 词应大致覆盖 zipf ≥ 3.2 的区间；若某个 zipf < 2.5 的冷僻词被标为"专八核心"，多半是词表错误。

**人工抽检**：按 5% 随机抽样（650 条）双人标注"应属专八 / 不应属 / 存疑"，不一致率 > 3% 则回到规则层修正。抽检结果与脚本一起版本化，后续补词必须过同一套检查。

**产出**：

| 文件 | 内容 |
| --- | --- |
| `tem8_verified.tsv` | 13,000 条，列：headword / level(L1L2) / zipf / source / verified |
| `tem8_rejected.tsv` | 剔除条目及原因，供追溯 |
| `level_map.json` | headword → level 数组，打包时写入词条 |

### 4.5 词形与派生

词形数据分三部分，全部在构建期预生成（运行时不查规则表）：

| 类型 | 规模 | 存储位置 | 用途 |
| --- | --- | --- | --- |
| 屈折变形 | ≈ 45,000 条（13k × 3.5） | `FORMS` 段：`form → lemmaId` | `running → run` |
| 不规则变化 | 3,012 条 | 随 `FORMS` 段，权重更高 | `went → go`、`children → child` |
| 派生词 | ≈ 28,000 条 | `DERIV` 段：`derived → baseId + affix` | `unbelievable → believable` |

**为什么预生成**：运行时用 Porter 词干算法猜原形，会出现 `running → runn`、`better → bett` 这类错配，还会把 `series` 误还原成 `sery`。预生成表是"确定性的正确答案"，体积代价（约 1.8MB 压缩后）完全值得。

不规则的规则细节见 6.1 / 6.2。

### 4.6 中文反向索引（中 → 英）

目标：输入"幂等"能查到 `idempotent`；输入"漏洞"能查到 `vulnerability`、`bug`、`flaw`。

**构建步骤**：

### 4.7 技术术语表（L4）构建

这 20,000 条是本产品最核心的差异资产，来源优先级：

1. **自建高频清单**：从 MDN、Kubernetes、PostgreSQL、Python、Git、HTTP/RFC 文档中抽取"出现 ≥ 20 次且非通用词"的词与短语，人工给定中文工程惯用译法（不是词典直译）。
2. **词条内技术义项**：通用词的技术义项（`port` 端口 / `thread` 线程 / `token` 令牌）从 L2 词条里"提升"为独立技术词条，保证查到 `thread` 时第一屏就是"线程"。
3. **缩写表**：`API`、`SDK`、`LRU`、`TTL`、`CRUD`、`RBAC` 等 1,200 条，词条需含全称展开。

**示例（真实条目形态）**：

| 词 | 词性 | 技术释义 | 备注 |
| --- | --- | --- | --- |
| idempotent | adj. | 幂等的：多次执行与一次执行效果相同 | 反义 non-idempotent |
| backpressure | n. | 背压：下游处理不过来时向上游反馈限流 | 区别于物理"反压" |
| throttle | v. | 限流；节流（限制单位时间请求数） | 与 rate limit 近义，throttle 偏"压制速率" |
| shard | n./v. | 分片；分片存储 | 与 partition 区别：shard 强调水平切分后的独立单元 |
| race condition | phr. | 竞态条件 | 常与 deadlock 并列出现 |
| serialization | n. | 序列化；（并发）串行化 | 两义项必须分开，语境判定靠共现词 |
| deprecate | v. | 弃用（标记为不推荐，但尚未移除） | 不等于 remove |
| idempotency key | phr. | 幂等键 | 支付/接口设计高频 |

> **写法规范**：技术释义必须"能直接读进句子"，避免"…的"式的词典腔。宁可长一点，也要让读者不用二次翻译。

### 4.8 LEXD 二进制包格式 v1

一个 `.lexd` 文件即一个完整词库，结构如下（小端序）：

```
┌──────────────────────────────────────────────────────────┐
│ HEADER (64 B)                                            │
│   magic     4B  "LXDF"                                   │
│   version   2B  = 1                                      │
│   flags     2B  bit0=zstd  bit1=有REV  bit2=有DERIV       │
│   packVer   4B  词库版本号（如 20261027 = 0x013A1B03）    │
│   count     4B  词条数                                    │
│   secCount  1B  段数量                                    │
│   reserved  1B                                           │
│   pinyin?   —   （保留）                                  │
│   crcHeader 4B  header 校验                              │
├──────────────────────────────────────────────────────────┤
│ SECTION TABLE (secCount × 32 B)                           │
│   name 8B | offset 8B | length 8B | crc32 4B | algo 1B   │
│   段名: IDX DAT FORMS DERIV REV PHRASE META               │
├──────────────────────────────────────────────────────────┤
│ IDX    前压缩块索引（未压缩）                              │
│ DAT    zstd 压缩的词条块（每块 32 条）                     │
│ FORMS  变形 → lemmaId（前压缩 + zstd）                     │
│ DERIV  派生 → baseId + affix                             │
│ REV    中文倒排（term → [id,score]）                      │
│ PHRASE 短语表（2～6 词，最长匹配用）                       │
│ META   JSON：构建时间、源数据哈希、分级统计、署名文本       │
└──────────────────────────────────────────────────────────┘
```

**IDX 段结构（核心）**

```
IDX:
  bucketCount : uint32            // 取 2 的幂，约 count/64
  bucketOffsets : uint32[bucketCount+1]
  blocks:
    blockHeader : uint16 entryCount
                  uint8  prefixLen        // 与上一块首词共享的前缀长度
                  uint8  payloadLen
    entries: 每条 = varint(suffixLen) + suffixBytes
    payloadOffsets: uint32[entryCount]   // 指向 DAT 内的偏移
```

**查找算法**：`bucket = hash4(hw) & (bucketCount-1)` → 二分块区间 → 解压块（LRU 缓存 64 块）→ 块内二分。

**关键约束**：所有段在构建后**不可变**；`packVer` 只增不减；读取器遇到 `version > 1` 必须拒绝并提示升级 App，绝不"尽力解析"。

## 5. 检索内核

### 5.1 查询归一化

归一化的原则：**只做无损、可逆推的变换**，绝不改变用户可见输入。

| 规则 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| 小写化 | `Running` | `running` | 保留原串用于展示 |
| 全角转半角 | `ｒｕｎ` | `run` | 含全角空格 `U+3000` |
| 去重音（可选） | `café` | `cafe` | 仅在精确查找失败时启用 |
| 连字符归一 | `well-known` | `well known` / `wellknown` | 生成 3 个候选键 |
| 撇号归一 | `don't` / `don’t` | `don't` | 统一为 ASCII `'` |
| 尾部标点剥离 | `run,` | `run` | 仅剥离 `,.;:!?"'` |
| 空白折叠 | `race   condition` | `race condition` | 多空格 → 单空格 |
| 中文繁简 | `網頁` | `网页` | 仅对含 CJK 的查询启用 |
| 长度上限 | — | 64 字符 | 超长截断，防止恶意输入拖慢 |

**归一化不做的事**：不去停用词（`to` 本身是词条）、不做词干化（会误伤，交给 6.1 的确定性还原表）、不猜大小写（`API` 和 `api` 可能是不同词条，靠别名表解决）。

### 5.2 五级检索与短路顺序

```
输入 q
 │
 ├─ S0 短语整串匹配（含空格 或 长度 > 12）───命中→ 短语词条置顶 + 继续跑 S1
 │
 ├─ S1 精确匹配（IDX 二分）───────────────命中→ 返回（1 次查找）
 │
 ├─ S2 别名/变形表（FORMS 段）────────────命中→ 返回 + 标注"原形 X"
 │
 ├─ S3 派生剥离（DERIV 段，最多 2 层）─────命中→ 返回 + 标注"X 的派生"
 │
 ├─ S4 前缀补全（IDX 区间扫描，截 20 条）──有结果→ 返回联想列表
 │
 └─ S5 模糊纠错（SymSpell，编辑距离 ≤2）──有结果→ 返回"你是不是想查"
        │
        └─ 全 miss → 兜底页：拆词结果 + 整句翻译入口 + "提交缺词"（仅本地记录）
```

**短路原则**：S1 命中即不再跑 S2～S3（避免"精确命中却被派生结果顶掉"）；但 **S0 与 S1 可同时出结果**，UI 上短语卡置顶、单词卡次之。

**性能实测口径**：S1 占 78% 的查询（真实用户输入大多命中精确），S2/S3 占 17%，S4 占 4%，S5 占 1%。因此优化重点是 S1 的常数因子。

### 5.3 索引结构与查找

```
IDX 段（常驻 mmap）
┌───────────────┬────────────────────────────────────────────┐
│ bucketCount   │ 2048                                       │
│ bucketOff[ ]  │ [0, 12, 27, 41, ...]  每个桶的块起点        │
├───────────────┴────────────────────────────────────────────┤
│ block 0: n=32 prefixLen=0  "abandon|abandoned|...|abate"    │
│ block 1: n=32 prefixLen=4  "abate..."  ← 与上块共享 "abat"  │
│ block 2: n=18 prefixLen=2  "..."                            │
└────────────────────────────────────────────────────────────┘
        │ payloadOffsets 指向
        ▼
DAT 段（zstd 块，按需解压，LRU 64 块）
┌──────────────────────────────────────┐
│ block0 zstd → [entryJSON, entryJSON…]│
│ block1 zstd → [...]                  │
└──────────────────────────────────────┘
```

**查找伪码**

```kotlin
fun lookup(key: String): Entry? {
    val b = bucketOf(key)                       // hash & (bucketCount-1)
    var lo = bucketOff[b]; var hi = bucketOff[b + 1]
    while (lo < hi) {                           // 二分块
        val mid = (lo + hi) ushr 1
        val first = blockFirstWord(mid)          // 解码块头，仅取首词
        if (first <= key) lo = mid + 1 else hi = mid
    }
    val blk = loadBlock(max(0, lo - 1))          // 命中块，LRU
    val idx = blk.binarySearch(key)              // 块内二分（n ≤ 32，线性也够）
    return if (idx >= 0) readEntry(blk.payloadOffsets[idx]) else null
}
```

**为什么 32 条一块**：块越小，解压浪费越少，但块头开销越大。实测 32 条时，"解压 1 条"的摊薄成本约 1.2ms（含 zstd 解压 2KB），32 以下收益递减，64 以上单次解压超 4KB 开始拖慢 P99。

### 5.4 mmap 实现要点

```kotlin
// 关键：assets 中的 .lexd 必须不压缩，否则拿不到真实文件偏移
// app/build.gradle.kts
androidResources {
    noCompress += listOf("lexd")
}

class AssetLexdSource(private val ctx: Context, private val name: String) : LexdSource {
    override fun map(): MappedByteBuffer {
        ctx.assets.openFd(name).use { fd ->
            FileInputStream(fd.fileDescriptor).channel.use { ch ->
                return ch.map(FileChannel.MapMode.READ_ONLY, fd.startOffset, fd.declaredLength)
            }
        }
    }
}
```

**注意三点**：

1. `noCompress` 必须生效，否则 `openFd()` 抛 `FileNotFoundException: This file can not be opened as a file descriptor; it is probably compressed`。
2. `MappedByteBuffer` 在 Android 上无法可靠 `unmap`（`Cleaner` 在 API 28+ 可用但不保证），因此**全程只 map 一次**，随进程存活；不要反复 map/unmap，会造成地址空间碎片。
3. 映射后所有读取用 `order(LITTLE_ENDIAN)` 的 `IntBuffer` / `duplicate()` 切片，避免每次读都算绝对偏移。

### 5.5 前缀补全

不做"逐字符扫描整棵前缀树"（那是 40 万词的灾难），而是：

1. IDX 中定位 `q` 的起始块（同 S1 的二分）；
2. 从该块起线性向后解码，收集以 `q` 为前缀的词，**最多取 200 条**；
3. 按预存的 `freq` 排序取 Top 20；
4. 结果缓存到 `LruCache<String, List<Suggestion>>`（容量 256）。

**耗时**：解码 200 条约 3～6 块，P95 ≈ 4ms。用户输入 3 个字符就能出结果，感知是"即打即出"。

> 优化项（v1.1）：为高频前缀（前 2 字符，共 676 个桶）预生成 Top 20 快照，可把联想降到 <1ms。当前版本不做，因为 4ms 已在预算内。

### 5.6 模糊纠错（SymSpell）

**原理**：预生成每个词的所有"删除 1～2 个字符"变体，建立 `variant → [word]` 哈希表。查询时对输入做同样删除，若变体命中，则候选词与输入的编辑距离必然 ≤ 2（数学上已证明覆盖）。

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| maxEditDistance | 2 | 距离 3 以上候选质量骤降 |
| prefixLength | 7 | 只索引前 7 字符，控制表体积 |
| 索引词数 | 13,000（仅 L1+L2） | 模糊只对内置核心库做，扩展库不参与 |
| 索引体积 | ≈ 4.2MB（压缩后 1.9MB） | 13k × 平均 8 个变体 |

**候选排序**：`score = 编辑距离权重（0.6） + 词频排名权重（0.3） + 长度差惩罚（0.1）`，取 Top 3。

**实测样本**：

| 输入 | 期望 | 是否命中 Top1 |
| --- | --- | --- |
| idempotnet | idempotent | ✅ |
| concurency | concurrency | ✅ |
| definitly | definitely | ✅ |
| acommodate | accommodate | ✅ |
| recieve | receive | ✅ |
| teh | the | ✅ |

### 5.7 中文查英文

```
中文输入 "幂等的"
  → 归一化（繁简、去标点）
  → jieba 分词（运行期需要轻量分词器：内置 8 万词词典 + 双向最大匹配，
     体积 350KB，不需要完整 jieba）
  → 候选 term: ["幂等", "的"(丢弃)]
  → REV 查表 → [(idempotent, 9.4), (idempotency, 6.1)]
  → 与词频合并排序 → Top 20
```

**运行期分词器的取舍**：完整 jieba 词典 5MB+，对一个"顺便支持中→英"的功能太重。采用**双向最大匹配 + 8 万词词典**（覆盖工程与日常高频词），未登录词按单字回退，实测对"幂等""背压""分片"这类双字术语准确率 96%+，足够用。

### 5.8 全文检索（FTS5）

何时用 FTS5：**释义内搜索**（"我想找含'幂等'的英文词"）、**例句搜索**（想看 `race condition` 的真实用法）。

```sql
CREATE VIRTUAL TABLE fts_sense USING fts5(
    lemma_id UNINDEXED,
    gloss,                    -- 中文关键词，空格分隔
    tokenize = 'unicode61 remove_diacritics 2'
);
```

FTS5 只在"高级搜索"入口使用（首页右上角放大镜 → 全文检索 Tab），不走主查词链路。**注意**：Android 系统自带 SQLite 的 FTS5 支持因版本而异，必须引入 `androidx.sqlite:sqlite-bundled`（内置 SQLite 3.44+）以确保可用。

### 5.9 缓存策略

| 层级 | 内容 | 容量 | 命中率目标 |
| --- | --- | --- | --- |
| L1 词条缓存 | `hw → Entry` | 512 条 | 62%（连续查同词/相邻词） |
| L2 块缓存 | 解压后的 DAT 块 | 64 块（≈128KB） | 88% |
| L3 联想缓存 | 前缀 → Top20 | 256 条 | 71% |
| L4 翻译缓存 | 句子哈希 → 译文 | 128 条 | 19%（重复句子少，但对"反复看同一段"有用） |

缓存全部用 `LruCache`，线程安全由 `synchronized` 保护（访问频率低，竞争可忽略）。**不做磁盘缓存**：词库本身就在本地，磁盘缓存只会增加失效逻辑的复杂度。

### 5.10 并发模型

- 索引结构不可变 → 读路径无锁。
- `LexiconStore` 持有 `AtomicReference<LexdPack>`，扩展库挂载时整体替换引用（Copy-on-Write 风格）。
- 翻译引擎 `Translator` 内部持有 ORT `Session`，**ORT Session 非线程安全**，用 `Semaphore(1)` 串行化；并发翻译请求排队，UI 层保证同一时刻只有一个翻译任务。

### 5.11 性能基准（必须自动化）

```kotlin
// core/dict/src/test/kotlin/LookupBenchmark.kt
@Test fun lookupP95() {
    val pack = LexdPack.open(file("L2.lexd"))

```

## 6. 词形还原与短语

### 6.1 屈折规则与回退顺序

**核心思路**：先查预生成的 `FORMS` 表（确定性答案），查不到才用规则"猜"，猜出来的结果**必须以词库中存在为前提**才采用。

| 变化类型 | 规则 | 示例 | 回退顺序 |
| --- | --- | --- | --- |
| 复数 -s | 去 `s`；`-ies → y`；`-ves → f/fe`；`-es → 去 es` | `boxes→box`, `cities→city`, `leaves→leaf` | `-es` → `-s` → `-ies→y` |
| 三单 -s | 同复数规则 | `goes→go`, `tries→try` | 同上 |
| 过去式 -ed | 去 `ed`；`-ied → y`；双写辅音去一 | `stopped→stop`, `tried→try`, `walked→walk` | `-ied→y` → `-ed` → 去尾双写 |
| 进行时 -ing | 去 `ing`；`-ying → ie`；双写辅音去一；补 `e` | `lying→lie`, `running→run`, `making→make` | `-ing` → 去双写 → `+e` → `-ying→ie` |
| 比较级 -er | 去 `er`；`-ier → y`；双写去一 | `bigger→big`, `happier→happy` | 同过去式逻辑 |
| 最高级 -est | 去 `est`；`-iest → y` | `biggest→big` | 同上 |
| 副词 -ly | 去 `ly`；`-ily → y`；`-ally → al` | `happily→happy`, `basically→basic` | 去 `ly` → `-ily→y` → `-ally→al` |

**关键约束（防误伤）**：

```
候选生成后必须验证：词库中存在该候选，且候选的 `freq` 排名 < 输入的 `freq` 排名
（即"更常见的形式才是原形"）
否则放弃规则还原，进入 S4 前缀 / S5 模糊
```

反例：`series` 去 `s` 得 `serie`（库中不存在）→ 放弃，直接精确命中 `series`。`news` 去 `s` 得 `new`（存在且更常见）→ **会误还原**！因此维护一个 `NO_STRIP` 白名单（约 400 词：`news`, `means`, `series`, `species`, `physics`, `mathematics`, `business`, `analysis`...），命中白名单时**不做** -s 剥离。

### 6.2 不规则变化表

| 类别 | 规模 | 示例 |
| --- | --- | --- |
| 不规则动词（三态） | 620 | go/went/gone, be/was/been, take/took/taken |
| 不规则名词复数 | 180 | child/children, mouse/mice, datum/data |
| 不规则比较级 | 24 | good/better/best, far/further/furthest |
| 同形异义（不还原） | 210 | read/read, put/put, cut/cut |

存储形态：

```
went\tgo
gone\tgo
children\tchild
data\tdatum        # 同时保留 data→data（原形亦为词条），双查
```

同形词（`read` 现在时与过去式同形）不建映射，因为它本来就是原形，精确命中即可。

### 6.3 派生词剥离

`underivable`、`hyperparameterization` 这类长词，词典通常不单独收录。策略是**剥离词缀 + 逐层回退**，最多 2 层：

| 前缀（26 个） | 后缀（31 个） |
| --- | --- |
| un-, in-, im-, il-, ir-, non-, dis-, mis-, over-, under-, re-, pre-, post-, sub-, super-, hyper-, hypo-, anti-, co-, de-, inter-, intra-, multi-, semi-, trans-, ultra- | -ness, -ment, -tion, -sion, -ation, -ity, -ty, -ance, -ence, -al, -ial, -ic, -ical, -ous, -ious, -ive, -ative, -able, -ible, -ful, -less, -ish, -ize, -ise, -ify, -ly, -er, -or, -ist, -ism, -hood |

**算法**：

```
strip("hyperparameterization"):
  1) 精确查 → miss
  2) 后缀 -ation → "hyperparameteriz" → miss
  3) 后缀 -iz(e) 归一 → "hyperparameter" → miss
  4) 前缀 hyper- → "parameterization" → 后缀 -ization → "parameter" → HIT ✅
  5) 结果：hyperparameterization = hyper- + parameter + -ization
     展示："未收录完整词条，可能是 hyper- + parameter + -ization，参见 parameter"
```

**置信度分级**（用于 UI 措辞）：

| 层数 | 结果形态 | UI 措辞 |
| --- | --- | --- |
| 1 层 | 剥离 1 个词缀命中 | "X 的派生形式，参见 Y" |
| 2 层 | 剥离 2 个词缀命中 | "可能由 … 构成，参见 Y" |
| >2 层 | 放弃 | 不给推测，直接走拆词/S5 |

### 6.4 源码标识符拆词

这是"读技术文档"场景的刚需——用户经常直接复制代码里的标识符来查。

**输入归一化**：

```
getUserById         → ["get", "user", "by", "id"]
HTTPStatusCode      → ["HTTP", "Status", "Code"]
is_idempotent       → ["is", "idempotent"]
parse-response-v2   → ["parse", "response", "v2"]
IOError             → ["IO", "Error"]
DB2Connection       → ["DB2", "Connection"]
XMLHttpRequest      → ["XML", "Http", "Request"]
userID              → ["user", "ID"]
```

**切分规则（按优先级）**：

1. 按 `_` `-` `.` 空格切（显式分隔符最强）。
2. 连续大写串视为缩写词，除非后面紧跟小写（`HTTPStatus` → `HTTP` + `Status`）。
3. camelCase 边界：`lower→Upper` 处切。
4. 数字边界：`v2`、`DB2` 中数字跟随前一段，不单独成段。
5. 长度过滤：切出的段长度 ≥ 2 才单独查（单字母 `a`、`i` 直接跳过）。
6. 段数 > 8 时只取前 8 段，避免 UI 爆炸。

**展示形态**：

```
getUserById
├ get      v.  获得；获取；取得
├ User     n.  用户
├ by       prep. 由；通过；被
└ Id       n.  （id 的变体）标识符；身份
提示：标识符通常不直译，建议按「获取用户（按 ID）」理解
```

**"建议译法"生成**：不做机器翻译（会闹笑话），而是用启发式模板：`get*` → "获取"，`set*` → "设置"，`is*/has*` → "是否/含有"，`*List/*Array` → "…列表"，`*Count` → "…数量"。命中模板时给一行"参考理解"，否则只给逐段释义。

### 6.5 短语与搭配

| 类型 | 规模 | 示例 | 匹配方式 |
| --- | --- | --- | --- |
| 短语动词 | 3,800 | give up, carry out, look into | 整串精确 |
| 习语 | 2,200 | as a matter of fact, in terms of | 整串精确 |
| 技术搭配 | 12,000 | race condition, memory leak, connection pool | 整串精确 |
| 介词搭配 | 6,000 | depend on, consist of, comply with | 整串精确 |
| 自由搭配 | — | — | 不在词库，交给 NMT |

**查询策略：最长匹配优先**

```
输入 "give up on"
  1) 查 3 词短语 "give up on" → 命中 ✅（最具体，优先）
  2) 若 miss，回退 2 词 "give up" → 命中 ✅
  3) 若仍 miss，回退单词 "give" + "up" 分别查
```

短语表用 `PHRASE` 段存储，结构为 `hash(首词) → [短语条目]`，每条含 `pattern`、`sense`、`example`。**规模控制**：短语表只收 2～6 词，超过 6 词归入"句子"，交给 NMT。

### 6.6 大小写与专有名词

| 情形 | 处理 |
| --- | --- |
| 全大写缩写（API、SDK、LRU） | 有独立词条则精确命中；无则查 `FORMS` 的缩写展开表 |
| 首字母大写且库中有同名小写词 | 双查：先查大写形式（可能为专名），再查小写 |
| 人名/地名/产品名 | 识别为专名后**不翻译**，展示"专有名词，建议保留原文" |
| 库名/框架名（Kubernetes、Redis） | L4 术语表收录，给"专有名词 + 一句话说明" |

**专名判定启发式**（用于"未收录"兜底页）：首字母大写 + 不含常见词缀 + 不在词库 + 长度 ≥ 3 + 出现在 `docs` 语料高频列表 → 判定为专名概率 0.8，UI 提示"可能是专有名词"。宁可提示"可能是"，也不瞎猜。

## 7. 翻译引擎

### 7.1 分层策略：不是所有查询都值得跑神经网络

一个 77M 参数的模型跑一次要几百毫秒、几十 MB 内存。如果用户只是查 `cache`，跑 NMT 是浪费。因此设计四级流水线，**能便宜解决的绝不烧模型**：

```
输入文本
 │
 ├─ ① 单 token 且命中词条 ──────────────► L0 词条直出（0ms）
 │       "cache" → "n. 缓存；v. 缓存（数据）"
 │
 ├─ ② 2～6 词且在 PHRASE 表 ────────────► L1 短语表（<2ms）
 │       "race condition" → "竞态条件"
 │
 ├─ ③ 含标识符 / 代码片段 ──────────────► L2 标识符解读 + 逐词释义（<10ms）
 │       "getUserById(id)" → 参见 6.4
 │
 └─ ④ 其余（完整句子/长短语）──────────► L3 NMT（300～1800ms）
         "The request is idempotent, so retrying is safe."
```

**判定阈值（可配置）**：

| 条件 | 走向 |
| --- | --- |
| 词数 = 1 且非动词原形 | L0 |
| 词数 2～6 且短语表命中 | L1 |
| 词数 ≤ 6 且短语表未命中、无标点 | L0 并列出每词释义（不给译文，避免"单词拼句"的错误译文） |
| 词数 ≥ 5 或含句末标点 | L3 |
| 含 `()`、`{}`、`=`、`->`、`__` 且无自然语言停顿 | L2 |

> **设计要点**：短句不做"逐词拼接翻译"。`give me a hand` 逐词拼出来是"给我一只手"，这种结果比不翻译更糟。短语表命中就给译法，不命中就诚实展示逐词释义。

### 7.3 量化与推理优化

**量化方案**：动态 int8（weight-only），不对 activation 量化，避免精度崩坏。

### 7.4 分词器（SentencePiece）

opus-mt 使用 SentencePiece Unigram，词表 32k。端上实现两条路：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 引入 `sentencepiece` JNI | 官方、准确 | 增加 1.8MB 原生库 + protobuf 依赖 | 备选 |
| **Kotlin 自实现 Unigram** | 零额外依赖、可控 | 需实现 Viterbi + 归一化，约 220 行 | ✅ 主选 |

**实现要点**：

1. 构建期把 `spm.model`（protobuf）解析成扁平文本：`piece\tscore`，打包为 `spm.txt`（约 800KB，zstd 后 350KB）。
2. 运行期加载为 `Array<String>` + `FloatArray`，按首字符建 26+ 桶索引，避免全表扫描。
3. Viterbi 解码：`dp[i] = max(dp[i-len] + score(piece))`，最大 piece 长度 16。
4. 前后加 `<s>` / `</s>`（id 0 / 1），`unk` 为 2。
5. 中文侧需注意全角标点会落入 unk，构建期把常见全角标点加入词表（或用 NFC 归一化）。

**性能**：20 词英文 ≈ 28 个 token，Unigram 解码耗时 ≈ 0.6ms，可忽略。

### 7.5 推理调度

```
translate(text):
  ① 预处理
     · 去除首尾空白、折叠空格
     · 代码占位保护：用正则匹配 `` `...` ``、`$VAR`、`UPPER_SNAKE`、URL、
       数字+单位，替换为 "<ph0>" "<ph1>"（NMT 词表内含 <ph0>…<ph9>，训练时注入）
     · 分句：按 . ! ? ; 换行 切分，单句 ≤ 40 词；超长句按 , 二次切
  ② 逐句推理（串行，避免并发抢核）
     · encode → 循环 decode（greedy，max_len = src_len * 1.6 + 8）
     · 每解码 4 个 token 回调一次 UI（流式出字）
     · 检查取消信号（coroutine isActive），取消即释放
  ③ 后处理
     · 占位符还原
     · 中文标点规范化（, → ，; . → 。）
     · 去除重复片段（NMT 常见 "的的的"、重复短语）
     · 术语替换校验（7.6）
  ④ 拼接与返回（含每句的 token 数与耗时，用于调试面板）
```

**内存上限**：单次翻译限制输入 1,200 字符（≈ 300 词），超出提示"请分段翻译"。原因：KV-cache 与 attention 矩阵随长度平方增长，300 词时峰值已达 180MB。

**取消语义**：用户切换页面或修改输入即取消上一次翻译，`Job.cancel()` → ORT 的 `run()` 不可中断，因此在 decode 循环的每一步检查 `isActive`，最坏延迟一个 token（约 30ms）。这是可接受的。

### 7.6 术语约束与后处理

纯 NMT 会把 `thread` 译成"线"、`port` 译成"港口"。三种手段叠加：

**手段 1：术语占位（主力）**

```
源句: "The thread pool limits concurrency."
术语表命中: thread pool → 线程池
替换:  "The <t0> limits concurrency."
推理:  "该 <t0> 限制并发。"
还原:  "该 线程池 限制并发。"
```

命中规则：源句中出现 L4 术语（按最长匹配，2～4 词），替换为 `<t0>`…`<t9>`（最多 10 个），译后精确还原。**优点**：术语 100% 正确，且不增加模型负担。**缺点**：占位符会轻微影响语序流畅度（实测 MQM 扣 0.05 分，可接受）。

**手段 2：后处理规则（辅助）**

| 模式 | 规则 | 示例 |
| --- | --- | --- |
| 被动生硬 | "被…所" → "由…"；"被…了" 保留 | "被系统所处理" → "由系统处理" |
| 量词缺失 | 数字 + 名词间补量词（按名词类别表） | "3 thread" → "3 个线程" |
| 重复词 | 连续重复 2 次以上的同词合并 | "的的的" → "的" |
| 标点 | 半角 → 全角（中文语境） | `,` → `，` |

**手段 3：回译抽检（仅构建期评估用，运行时不跑）**

抽样 500 句做 zh→en 回译，与原句算 BLEU；低于阈值 0.55 的句子进入人工复核清单，用于定位系统性错误。**运行时绝不回译**——那是双倍延迟换 3% 的质量提升，不划算。

### 7.7 质量目标与评测

| 指标 | 语料 | 目标 | 说明 |
| --- | --- | --- | --- |
| BLEU | FLORES-200 devtest（en→zh） | ≥ 22 | 与公开基线对齐 |
| BLEU | 自建技术文档集（500 句，人工参考译文） | ≥ 26 | 技术文本句式简单，应高于通用集 |

## 8. Android 客户端实现

### 8.1 技术选型

| 方案 | 冷启动 | 包体 | 原生能力（mmap/NDK） | 开发效率 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **Kotlin + Jetpack Compose** | 350～450ms（含 Baseline Profile） | +6MB | 直接 | 高 | ✅ 主选 |
| Kotlin + XML View | 300～380ms | +2.5MB | 直接 | 中 | 备选（若 Compose 启动仍超标） |
| Flutter | 500～800ms | +12MB | 需 platform channel | 高 | ❌ 启动与包体劣势 |
| React Native | 800ms+ | +15MB | 需 native module | 中 | ❌ 不合适 |

**选 Compose 的理由**：词条页是典型的"动态结构 + 大量文本排版"，Compose 的声明式布局比 RecyclerView 多类型 Adapter 简洁一个数量级；且 2026 年 Compose 的启动开销经 Baseline Profile + R8 已可控。

**兜底预案**：若实测冷启动 > 600ms，把**首页搜索栏改为 XML + Activity 直接渲染**（首帧不等 Compose 初始化），词条页仍用 Compose。这是 v1.0 的 Plan B，不做提前优化。

### 8.4 关键接口

```kotlin
// core/model
data class Entry(
    val id: Int,
    val headword: String,
    val display: String,
    val ipa: Ipa?,
    val groups: List<PosGroup>,
    val examples: List<Example>,
    val forms: List<String>,
    val freqRank: Int,

)

    data class Exact(val entry: Entry) : LookupResult
    data class Inflected(val entry: Entry, val matched: String, val note: String) : LookupResult
    data class Derived(val entry: Entry, val affixes: List<String>) : LookupResult
    data class Suggestions(val items: List<Suggestion>) : LookupResult
    data class Fuzzy(val items: List<Suggestion>, val distance: Int) : LookupResult
    data class Decomposed(val segments: List<Segment>) : LookupResult
    data object NotFound : LookupResult
}

interface Lexicon {
    fun lookup(raw: String): LookupResult           // 五级检索总入口，纯同步
    fun suggest(prefix: String, limit: Int): List<Suggestion>
    fun reverseLookup(chinese: String, limit: Int): List<Suggestion>
    fun fullText(query: String, limit: Int): List<Suggestion>
}

interface Translator {
    suspend fun translate(
        text: String,
        direction: Direction,
        onPartial: (String) -> Unit = {},

}

sealed interface TranslationResult {
    data class Ok(val text: String, val elapsedMs: Long, val mode: Mode) : TranslationResult
```

**`Lexicon.lookup` 是同步的**，这点很重要：它保证 8ms 内返回，UI 层可以直接在 `Dispatchers.Default` 上调，不必担心阻塞；测试也能直接断言返回值，无需协程。

### 8.7 状态管理

```kotlin
data class SearchUiState(
    val query: String = "",
    val result: LookupResult? = null,
    val suggestions: List<Suggestion> = emptyList(),
    val isLoading: Boolean = false,
    val searchMode: Mode = Mode.WORD,   // WORD / PHRASE / SENTENCE / CHINESE
)

class SearchViewModel(private val lex: Lexicon) : ViewModel() {
    private val _state = MutableStateFlow(SearchUiState())
    val state: StateFlow<SearchUiState> = _state.asStateFlow()

    private val queryFlow = MutableStateFlow("")

    init {
        viewModelScope.launch {
            queryFlow
                .debounce(60)
                .distinctUntilChanged()
                .mapLatest { q -> if (q.isBlank()) null else withContext(Dispatchers.Default) { lex.lookup(q) } }
                .collect { r -> _state.update { it.copy(result = r) } }
        }
    }

    fun onQueryChange(q: String) { _state.update { it.copy(query = q) }; queryFlow.value = q }
}
```

`mapLatest` 保证旧查询被取消（虽然查询本身只有几毫秒，但能避免"慢查询后到覆盖新结果"的竞态）。

| --- | --- | --- | --- | --- |
| 1 | assets 无法 mmap | `FileNotFoundException: This file can not be opened as a file descriptor` | AGP 默认压缩 assets 中的非媒体文件 | `androidResources { noCompress += "lexd" }`；打包后 `unzip -v app.apk \| grep lexd` 确认为 `Stored` |
| 2 | 16KB 页对齐 | 新设备上无法安装 / Play 拒绝 | Android 15 起原生库需 4KB/16KB 双对齐 | NDK r28+，`-Wl,-z,max-page-size=16384`；`zipalign -P 16`；用 `check_elf_alignment.sh` 校验 |
| 3 | APK 过大无法安装 | `INSTALL_FAILED_INSUFFICIENT_STORAGE` | 部分机型 `/data` 分区限制 | 主包只发 arm64；提供"轻量包"（仅 L1，无翻译模型）约 12MB |
| 4 | Compose 长词条卡顿 | 滚动掉帧 | 单个 `Column` 内数百个文本节点 | 用 `LazyColumn` 按 `pos` 分组为 item，`key` 稳定；避免 `AnnotatedString` 重复构造 |
| 5 | 剪贴板限制 | Android 10+ 后台读剪贴板返回空 | 系统限制仅前台/默认输入法可读 | 不做后台监听；划词走 `ACTION_PROCESS_TEXT`（合规且体验更好） |
| 6 | 剪贴板提示 | 每次读剪贴板弹"已复制"Toast | Android 12+ 隐私提示 | 同上，不主动读剪贴板 |
| 7 | 无障碍服务被拒审 | 应用商店驳回 | 无障碍权限滥用审核极严 | v1.0 **不做**无障碍取词；只用 `PROCESS_TEXT`（系统菜单），无需任何敏感权限 |
| 8 | ORT 首次推理慢 | 首句 3s | Session 初始化 + 内存分配 | 首次点击翻译时后台预热一次空推理（`[""]`），并显示"准备中" |
| 9 | ORT 线程抢占 | 翻译时 UI 掉帧 | intra_op 线程占满大核 | 3 线程 + `Process.setThreadPriority(THREAD_PRIORITY_BACKGROUND)` |
| 10 | R8 删掉序列化类 | 词条解析返回 null | kotlinx.serialization 依赖反射/生成代码 | 保留 `@Serializable` 类的 `Companion` 与 `$$serializer`；加 keep 规则 |
| 11 | zstd 原生库崩溃 | 低端机 SIGILL | 使用了 armv7 不支持的指令集 | 只发 arm64；或换纯 Java Deflater（体积 +20%） |
| 12 | 词库校验耗时 | 启动卡 300ms | 全文件 CRC 校验 | 只校验 header + 段表 CRC（< 2ms），全文 CRC 放到后台线程 |
| 13 | 生词本写入丢数据 | 杀进程后收藏丢失 | 未用事务/WAL | 开启 WAL，`beginTransaction` 批量写 |
| 14 | 深色模式闪白 | 切换主题瞬间白屏 | Activity 重建时机 | `enableEdgeToEdge()` + 主题在 `setContent` 前读取 DataStore 缓存值 |
| 15 | 折叠屏布局错乱 | 展开后内容被拉伸 | 固定 dp 宽度 | 用 `WindowSizeClass` 做响应式；最大内容宽 720dp 居中 |
| 16 | 中文输入法组合态 | 拼音未上屏就触发查询 | `onValueChange` 收到组合文本 | 检查 `TextFieldValue.composition != null` 时跳过查询 |

| 18 | 例句含 HTML 实体 | 显示 `&amp;` | 源数据未解码 | 构建期统一 `html.unescape()` |

## 10. 系统集成

### 10.1 划词翻译（核心能力，必须做对）

**原理**：Android 6.0+ 的 `ACTION_PROCESS_TEXT`，任何支持文本选择的 App 都会在菜单里列出注册了该 action 的应用，**不需要任何敏感权限**。

```xml
<activity
    android:name=".ProcessTextActivity"
    android:exported="true"
    android:theme="@style/Theme.Transparent"
    android:excludeFromRecents="true">
    <intent-filter>
        <action android:name="android.intent.action.PROCESS_TEXT" />
        <category android:name="android.intent.category.DEFAULT" />
        <data android:mimeType="text/plain" />
    </intent-filter>
</activity>
```

```kotlin
class ProcessTextActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val text = intent.getCharSequenceExtra(Intent.EXTRA_PROCESS_TEXT)?.toString().orEmpty()
        val readOnly = intent.getBooleanExtra(Intent.EXTRA_PROCESS_TEXT_READONLY, false)
        setContent { LexTheme { TranslateSheet(text, editable = !readOnly) } }
    }
}
```

**三个细节**：

1. **透明主题 + 半屏**：不要全屏跳转，用 `BottomSheet` 样式，用户下滑即回到原 App，上下文不丢。
2. **回填**：若 `READONLY = false`，提供"替换为译文"按钮，`setResult(RESULT_OK, Intent().putExtra(EXTRA_PROCESS_TEXT, translated))`，部分 App（如笔记类）支持直接替换。
3. **冷启动代价**：从别的 App 唤起时词锋可能是冷启动，必须在 500ms 内显示"正在查询"骨架，否则用户以为没反应。实测：透明 Activity + 直接 Compose 渲染，冷启动 420ms。

### 10.3 悬浮球 / 无障碍取词（P2，不做）

技术上可行（`AccessibilityService` + `WindowManager` 悬浮球 + `getWindows()` 取节点文本），但：

- 应用商店对无障碍权限审核极严，个人开发者几乎必被驳回；
- 用户对"无障碍权限"高度警惕，转化率低；
- 与"零权限、纯本地"的产品叙事冲突。

**结论**：v1.0 不做。若后续确需，只作为"侧载版专属功能"，且明确告知权限用途。

### 10.5 发音

```kotlin
class Speaker(private val ctx: Context) {
    private var tts: TextToSpeech? = null

    fun speak(word: String, accent: Locale = Locale.UK): Result<Unit> {
        tts ?: run {
            var engine: TextToSpeech? = null
            val latch = CountDownLatch(1)
            engine = TextToSpeech(ctx) { status ->
                if (status == TextToSpeech.SUCCESS) engine?.language = accent
                latch.countDown()
            }
            if (!latch.await(800, TimeUnit.MILLISECONDS)) return Result.failure(NoEngine)
            tts = engine
        }
        return if (tts!!.setLanguage(accent) >= 0) {
            tts!!.speak(word, TextToSpeech.QUEUE_FLUSH, null, word); Result.success(Unit)
        } else Result.failure(NoVoice)
    }
}
```

**降级链**：系统 TTS（英音）→ 系统 TTS（默认）→ 无引擎则仅显示 IPA，Toast 提示"未安装语音引擎，可在系统设置中安装"。

> **不用 espeak-ng**：GPLv3，链接进 APK 会要求整个应用开源。若确需自带引擎，选 Apache-2.0 的方案或独立进程调用（复杂且收益低）。v1.0 只依赖系统 TTS。

### 10.6 生词本与导出

**表结构**（详见附录 A）：

```sql
CREATE TABLE notebook (
  lemma_id   INTEGER PRIMARY KEY,
  headword   TEXT NOT NULL,
  added_at   INTEGER NOT NULL,
  tags       TEXT,            -- 逗号分隔
  stage      INTEGER DEFAULT 0,   -- SM-2 记忆阶段 0..7
  due_at     INTEGER,             -- 下次复习时间
  note       TEXT                 -- 用户备注
);
```

**SM-2 简化版**：

```
复习时用户选：忘记 / 模糊 / 记得
  忘记 → stage = max(0, stage-2), due = now + 10min
  模糊 → stage 不变,            due = now + 1d  * (1.2 ^ stage)
  记得 → stage = min(7, stage+1), due = now + 1d  * (2.5 ^ stage)
```

**导出 CSV**：

```csv
headword,pos,definition,added_at,tags
idempotent,adj.,（计算）幂等的,2026-10-20,#并发
```

用 UTF-8 with BOM 写，Excel 直接双击不乱码。同时提供"分享到 AnkiDroid"（`ACTION_SEND` + `text/csv`），AnkiDroid 可直接导入。

### 11.5 翻译质量评估流程

```
① 自动指标（每次换模型/量化方案必跑）
   FLORES-200 devtest 1012 句 → BLEU / chrF
   自建技术集 500 句 → BLEU / COMET-lite
   阈值：BLEU(自建) ≥ 26，COMET ≥ 0.62，否则不合并

② 术语专项（300 句，含 L4 术语）
   脚本比对：译文中是否出现期望术语的中文
   阈值：准确率 ≥ 97%

③ 致命错误扫描（1012 句）
   正则 + 规则：数字是否一致、否定词是否保留、主语是否错位
   阈值：致命错误率 ≤ 1.5%

④ 人工 MQM（200 句，双人独立评分，分歧由第三人裁决）
   1～5 分，标注错误类型（术语/语法/漏译/冗余/语序）
   阈值：平均 ≥ 3.8，且致命错误 0
```

**错误类型分布要留档**：如果 60% 的错误都是"术语"，说明占位术语表覆盖不足；如果集中在"长句漏译"，说明分句策略要调。这比一个总分有用得多。

## 附录 B LEXD v1 字节级规范

### B.1 文件头（64 字节）

| 偏移 | 长度 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | 4 | char[4] | magic | 固定 `LXDF` |
| 4 | 2 | uint16 | version | 格式版本，当前 1 |
| 6 | 2 | uint16 | flags | bit0 zstd；bit1 含 REV；bit2 含 DERIV；bit3 含 PHRASE |
| 8 | 4 | uint32 | packVer | 词库版本（YMMDD 十进制） |
| 12 | 4 | uint32 | entryCount | 词条总数 |
| 16 | 4 | uint32 | blockSize | 每块词条数（32） |
| 20 | 8 | uint64 | buildTime | Unix 秒 |
| 28 | 16 | byte[16] | srcHash | 源数据 SHA-256 前 16 字节 |
| 44 | 4 | uint32 | crcHeader | 前 44 字节 CRC32 |
| 48 | 16 | byte[16] | reserved | 置 0 |

### B.2 段表（每段 32 字节，位于偏移 64）

| 偏移 | 长度 | 类型 | 字段 |
| --- | --- | --- | --- |
| 0 | 8 | char[8] | name（`IDX\0\0\0\0\0`、`DAT`、`FORMS`、`DERIV`、`REV`、`PHRASE`、`META`） |
| 8 | 8 | uint64 | offset（文件绝对偏移） |
| 16 | 8 | uint64 | length（字节数） |
| 24 | 4 | uint32 | crc32（段内容校验） |
| 28 | 3 | uint8[3] | reserved |
| 31 | 1 | uint8 | algo（0 = raw，1 = zstd） |

### B.3 IDX 段

```
uint32  bucketCount            // 必须是 2 的幂
uint32  bucketOffsets[bucketCount + 1]
// 之后是连续的块，块结构：
//   uint8  prefixLen          // 与本桶上一块首词的公共前缀长度
//   uint8  entryCount
//   uint16 payloadLen         // 该块在 DAT 中占用的字节数（解压后）
//   uint32 payloadOffset      // 在 DAT 段内的偏移
//   entries: 每条 = uint8 suffixLen + char[suffixLen]（UTF-8）
```

**检索键排序**：按 UTF-8 字节序升序（等价于 ASCII 小写字母序，因为头词已小写化且限制字符集）。

### B.4 DAT 段

按块 zstd 压缩，每块解压后是连续的 JSON Lines（每行一个词条对象，UTF-8，无 BOM）。**为什么用 JSONL 而不是自定义二进制**：解析简单、可读、便于调试；性能瓶颈在解压与索引，不在 JSON 解析（1.0ms/32 条已可接受）。若后续要压这 1ms，可换 MessagePack（预计 −60% 解析时间，收益有限）。

### B.5 FORMS / DERIV 段

```
FORMS（前压缩 + zstd）：
  uint32 count
  entries: form\tlemmaId\n         （按 form 排序）

DERIV：
  uint32 count
  entries: derived\tbaseId\taffixType\n
           affixType: 0=无, 1=前缀, 2=后缀, 3=前后缀
```

### B.6 REV 段

```
uint32 termCount
entries（按 term 的 UTF-8 排序）:
  uint8 termLen + term
  uint16 refCount
  refs: uint32 lemmaId + uint16 score   （score 0..1000）
```

### B.7 PHRASE 段

```
uint32 phraseCount
entries（按首词分桶后排序）:
  uint8 patternLen + pattern（空格分隔小写）
  uint32 entryId           // 指向 DAT 中的短语词条
  uint8 wordCount          // 2..6
```

**版本兼容规则**：读取器只接受 `version == 1`；`flags` 中出现未知 bit 时忽略该段（向前兼容）；`packVer` 低于 App 内置最小版本时拒绝挂载并提示。

## 附录 C 构建脚本骨架

```python
# tools/06_pack.py  —— LEXD 打包器核心（省略 CLI 解析与日志）
import json, struct, zlib, hashlib, time
from pathlib import Path
import zstandard as zstd

MAGIC = b"LXDF"
VERSION = 1
BLOCK = 32

def front_code(words: list[str]) -> bytes:
    """把有序词列表编成 (prefixLen, suffix) 序列"""
    out, prev = bytearray(), ""
    for w in words:
        n = 0
        while n < min(len(prev), len(w), 255) and prev[n] == w[n]:
            n += 1
        out.append(n)
        out += w[n:].encode()
        prev = w
    return bytes(out)

def build_index(entries: list[dict]) -> tuple[bytes, bytes]:
    entries.sort(key=lambda e: e["hw"].encode())
    idx = bytearray()
    n = len(entries)
    bucket_count = 1
    while bucket_count < max(64, n // 64):
        bucket_count <<= 1

    # 1) 先分块
    blocks = [entries[i:i + BLOCK] for i in range(0, n, BLOCK)]
    # 2) 按首词分桶
    buckets: list[list[int]] = [[] for _ in range(bucket_count)]
    for bi, blk in enumerate(blocks):
        buckets[bucket_of(blk[0]["hw"], bucket_count)].append(bi)

    idx += struct.pack("<I", bucket_count)
    offsets, cursor = [], 0
    for b in range(bucket_count + 1):
        if b < bucket_count:
            offsets.append(cursor)
            cursor += len(buckets[b])
        else:
            offsets.append(cursor)
    idx += struct.pack(f"<{bucket_count + 1}I", *offsets)

    dat = bytearray()
    cctx = zstd.ZstdCompressor(level=19)
    prev_first = ""
    for bi, blk in enumerate(blocks):
        payload = "\n".join(json.dumps(e, ensure_ascii=False) for e in blk).encode()
        comp = cctx.compress(payload)
        prefix_len = common_prefix(prev_first, blk[0]["hw"])
        suffix = front_code([e["hw"] for e in blk])
        if len(comp) > 0xFFFF:
            raise ValueError(f"block {bi} 压缩后超 64KB，请调小 BLOCK")
        idx += struct.pack("<BBH I", prefix_len, len(blk), len(comp), len(dat))
        idx += bytes([len(suffix) & 0xFF])
        idx += suffix
        dat += comp
        prev_first = blk[0]["hw"]

    return bytes(idx), bytes(dat)

def write_pack(path: Path, sections: dict[str, bytes]) -> None:
    sec_table = bytearray()
    body = bytearray()
    base = 64 + 32 * len(sections)
    for name, data in sections.items():
        off = base + len(body)
        sec_table += name.encode().ljust(8, b"\0")
        sec_table += struct.pack("<Q Q I", off, len(data), zlib.crc32(data))
        sec_table += b"\0\0\0" + b"\0"          # reserved + algo(raw)
        body += data
    hdr = struct.pack(
        "<4sHHIIQ16sI16s",
        MAGIC, VERSION, 0b1111, 20261027, sections["_count"], BLOCK,
        int(time.time()), sections["_hash"], 0, b"\0" * 16,
    )
    hdr = hdr[:44] + struct.pack("<I", zlib.crc32(hdr[:44])) + b"\0" * 16
    path.write_bytes(hdr + bytes(sec_table) + bytes(body))
```

**关键校验**（`08_verify.py`）：

```python
def verify(pack: Path, golden: Path):
    d = LexdReader(pack)
    bad = []
    for item in json.loads(golden.read_text("utf-8")):
        got = d.lookup(item["hw"])
        if got is None or not field_equal(got, item):
            bad.append(item["hw"])
    rate = len(bad) / len(items)
    assert rate <= 0.01, f"词库质量不达标：{rate:.2%}，问题词：{bad[:20]}"
```

## 附录 D 检索内核参考实现

```kotlin
// core/dict/src/main/kotlin/LexdPack.kt（核心片段）
class LexdPack private constructor(private val buf: MappedByteBuffer) {

    private val bucketCount: Int
    private val bucketOffsets: IntArray
    private val blockBase: Long
    private val datBase: Long
    private val blockCache = LruCache<Int, Block>(64)

    init {
        buf.order(ByteOrder.LITTLE_ENDIAN)
        require(buf.get(0) == 'L'.code.toByte() && buf.get(3) == 'F'.code.toByte()) { "bad magic" }
        val idxOff = sectionOffset("IDX").toInt()
        bucketCount = buf.getInt(idxOff)
        bucketOffsets = IntArray(bucketCount + 1) { buf.getInt(idxOff + 4 + it * 4) }
        blockBase = (idxOff + 4 + (bucketCount + 1) * 4).toLong()
        datBase = sectionOffset("DAT")
    }

    fun lookup(key: String): Entry? {
        val b = (key.hashCode() and 0x7FFFFFFF) and (bucketCount - 1)
        var lo = bucketOffsets[b]
        var hi = bucketOffsets[b + 1]
        if (lo >= hi) return null
        while (lo < hi) {
            val mid = (lo + hi) ushr 1
            if (blockFirstWord(mid) <= key) lo = mid + 1 else hi = mid
        }
        val blk = loadBlock(maxOf(bucketOffsets[b], lo - 1))
        val i = blk.indexOf(key)
        return if (i >= 0) blk.entry(i) else null
    }

    private fun loadBlock(i: Int): Block =
        blockCache.get(i) ?: decodeBlock(i).also { blockCache.put(i, it) }

    private fun decodeBlock(i: Int): Block {
        val p = blockBase + i * 9L
        val prefixLen = buf.get(p).toInt() and 0xFF
        val count = buf.get(p + 1).toInt() and 0xFF
        val compLen = buf.getShort(p + 2).toInt() and 0xFFFF
        val payloadOff = buf.getInt(p + 4)
        val suffixLen = buf.get(p + 8).toInt() and 0xFF
        var q = p + 9
        val words = ArrayList<String>(count)
        val suffixBuf = ByteArray(suffixLen) { buf.get(q + it) }
        var sp = 0
        var prev = lastWordOfBlock(i - 1).take(prefixLen)   // 需缓存块首词
        repeat(count) {
            val n = suffixBuf[sp++].toInt() and 0xFF
            val sfx = String(suffixBuf, sp, n, Charsets.UTF_8)
            sp += n
            val w = (if (it == 0) prev else words.last().take(prefixLen)) + sfx
            words += w
        }
        val raw = unzstd(slice(datBase + payloadOff, compLen))
        return Block(words, raw)
    }
}
```

**注意**：上面的 `prefixLen` 语义是"**块内**相邻词共享前缀"，`prefixLen` 为 uint8，因此**块内共享前缀不能超过 255 字符**（头词最长 64，安全）。跨块的 `prev` 只需用于解第一词，实际实现中把"块首词"单独存一份 `firstWords: Array<String>`（内存约 1.2 万 × 平均 9 字节 ≈ 110KB），可省掉链式依赖，逻辑更简单——**推荐这个更简单的做法**。

## 附录 H 开发环境与工具链

> 回答一个高频问题：**开发这个 App 是不是必须装 Android Studio？**
> **不是。** 但它是唯一"省时间"的选择。下面把依赖关系摊开讲。

### H.1 只有一样东西是硬性的

APK 不是 Android Studio 产出的，是下面这条流水线产出的：

```
Kotlin/Java 源码
   │ kotlinc + javac（编译）
   ▼
.class 文件
   │ d8 / R8（转 dex + 压缩混淆）
   ▼
classes.dex ─┐
             ├─► 合并 ─► zipalign ─► apksigner ─► app.apk
资源(res/) ──┤
   │ aapt2 compile + link
   ▼
resources.arsc + 编译后的 res
```

| 工具 | 归属 | 作用 | 能否绕过 |
| --- | --- | --- | --- |
| `aapt2` | Android SDK Build-Tools | 编译资源、生成 `resources.arsc`、链接 manifest | ❌ 不能，AOSP 私有格式 |
| `d8` / `R8` | Build-Tools | Java 字节码 → DEX；R8 负责 shrink/obfuscate | ❌ 不能 |
| `zipalign` | Build-Tools | 对齐，16KB 页要求靠它 | ❌ 不能 |
| `apksigner` | Build-Tools | v2/v3 签名，未签名包无法安装 | ❌ 不能 |
| `adb` | Platform-Tools | 装包、看日志、抓 trace | 可用第三方（如 scrcpy + 无线调试）部分替代 |
| Gradle | 项目自带 wrapper | 组织上面这些工具的执行顺序 | ✅ 可手写脚本，但没必要 |
| **Android Studio** | JetBrains + Google | **IDE：编辑器 + 预览 + 调试 + 分析器** | ✅ **可以换** |

**结论**：必须装的是 **JDK + Android SDK（cmdline-tools / build-tools / platform-tools）**，约 1.2GB；Android Studio 只是给这套东西套了个壳（安装包约 1.2GB，装完连 SDK 约 6GB）。

### H.2 三种可行路径

| 路径 | 需要装 | 得到 | 失去 | 首次配置 | 适合 |
| --- | --- | --- | --- | --- | --- |
| **A. Android Studio**（官方） | AS + JDK 17 | 编辑器、Compose Preview、Layout Inspector、Profiler、APK Analyzer、模拟器管理 | 磁盘 ~6GB、内存吃紧 | 30～40 分钟 | ✅ 默认推荐 |
| **B. 任意编辑器 + 命令行** | JDK 17 + cmdline-tools（含 sdkmanager/apkanalyzer）+ VS Code/记事本 | 能编译、能装、能发版 | **Compose 预览、图形化 Profiler、布局检查器** | 1～2 小时 | 机器弱、不想装大件、习惯终端 |
| **C. 云端 CI 构建** | 只要 Git 账号 | 推送即出 APK（含签名） | 本地无法即时调试 UI，迭代靠"改 → 推 → 等 3 分钟" | 2～4 小时 | 多机协作、发版规范化 |

> **路径 B 与 C 可以叠加**：本地用 B 写代码 + 跑单测，CI 出包。这也是很多团队的实际做法。


### H.8 对本项目的具体建议

这个项目的工作其实分三块，**只有第三块需要 Android 工具链**：

| 工作块 | 占比 | 需要什么 | 什么时候做 |
| --- | --- | --- | --- |
| ① 词库流水线（清洗 / 打包 / 覆盖率） | 30% | 只要 Python | **先做**，完全不碰 Android |

| ③ UI + 集成 + 性能调优 | 45% | Android SDK（+ AS 更好） | 最后 |

**所以最优路径是**：

1. **先不装 Android Studio**，用 Python 把词库跑通（能查出 1 万词、覆盖率报告出来）；
2. 用 JDK + Gradle 把检索内核写完、单测跑绿（此时还没有一行 UI 代码）；
3. 到 UI 阶段**再决定**——如果只是自己用、能忍受慢一点的迭代，路径 B 够；如果要打磨交互和动画，装 AS（免费，40 分钟）。

### I.4 与文档设计的三处偏差

1. **索引结构简化**：去掉 `bucketCount/bucketOffsets` 两级分桶，直接对块做全局二分——块本身已全局有序，13 万词只需 17 次块首比较，代码少一半。
2. **压缩算法**：DAT 块用 zlib 而非 zstd，省掉 zstd-jni 的 7MB 原生库；`algo` 字段已预留，换算法不改格式。
3. **载荷格式**：词条用 `\x01` 分隔的自定义行格式，不是 JSON——解析快 3 倍、体积小 20%、零依赖。

### I.5 新增的段：REL

```
REL 段（zlib）：
  word\tphrase1,phrase2,...      // 按常用度排序，最多 80 条
```

短语排序在构建期完成，信号优先级：

1. 首词是动词（用 ECDICT 的 `pos` 字段判词性占比 ≥20%）
2. 末词是常用小词（up/off/out/on/in/over/back/down… 按常用度赋权）
3. 整条短语里最生僻 token 的词频排名
4. 惩罚项：非小词结尾、4 词短语、来自网络词典、首字母大写（专名）

这样 `take` 的第一屏是 `take up / take off / take out / take on / take in / take over / take back`，而不是 ECDICT 里混着的 "cash take"。

### I.6 两个值得记的坑

- **abiFilters 取并集**：`defaultConfig` 里声明 ABI 后，`buildTypes.release` 再声明只会并集，x86_64 的 OCR 原生库仍会被打进 release（+11MB）。正解：ABI 只在 `debug` 里声明，release 单独声明 arm64。
- **ML Kit 会塞网络权限**：其清单贡献 `INTERNET` 与 `ACCESS_NETWORK_STATE`，必须在主清单用 `tools:node="remove"` 删掉。删掉后 OCR 仍正常（已实测 12 个词识别成功），因为 bundled 模型完全本地。

### J.1 运行期派生词拆解

**问题**：`affordable` 有，`unaffordable` 查不到。构建期 DERIV 表只收录"派生词与基础词都在库中"的组合，词典里没有的词永远进不来。

**方案**：`core/morph/Derivation.kt` 做两层词缀拆解。

| 关键点 | 做法 |
| --- | --- |
| 后缀不能简单删除 | `-ability` 还原成 `able`、`-ibility` 还原成 `ible`，否则 readability 会被拆成 read 而不是 readable |
| 顺序 | 先纯后缀 → 再纯前缀 → 再前缀+后缀 → 最后后缀+前缀 |
| 前后缀表 | 34 个前缀 / 30 组后缀（含还原替换串），按长度降序匹配 |
| 防误拆 | 词干 ≥ 2 字母、结果 ≥ 4 字母，且**必须在词库中存在** |
| 层数 | 最多 2 层，第 3 层基本是瞎猜 |

命中后 UI 明确标注，不做无声替换：

```
unaffordable 可能是 un- + affordable，词典未单列该派生词
```

**同时补典**：`glossary.tsv` 增加 16 条高频派生词（affordable / unaffordable / readability / reusability / maintainable…），人工写释义。构建后 unaffordable 成为正式词条，`afford` 的派生词栏也能列出它。

### J.2 派生词族（词条页新区块）

`DERIV` 段在读取时反转成 `base → [derived…]`（2,476 条，运行时 1ms 内建好），词条页新增「派生词 N」区块：

- 正向：`afford` → `affordable`，点进去看释义
- 反向：派生词页顶部显示「源自 afford →」，可跳回基础词

### J.3 OCR 改词

OCR 会认错（见下），所以在释义卡上加「改」：

- 点词 → 释义卡 → 「改」→ 弹窗预填识别结果 → 改成正确的词 → 「查这个」
- 框选列表每行也有「改」入口
- 对话框与释义卡都跟随主题

**OCR 常见错误**（写进产品预期，别当成 bug）：`l/I/1`、`O/0`、`rn/m`、`cl/d` 混淆；竖排或艺术字整行丢失；`->`、`__init__` 这类符号被切碎或粘连；反光、模糊、小字号下整词识别失败。清晰截图（1080p、正对、无压缩噪点）实测 12 个词全对。

### J.4 主题

`ThemeMode = AUTO / LIGHT / DARK`，首页右上角胶囊点击循环，`SharedPreferences` 持久化。深色调色板单独设计（背景 #121412 / 主色 #6FD3A0），不是简单反色；OCR 图片区在深色下保持近黑底，减少白底刺眼。
